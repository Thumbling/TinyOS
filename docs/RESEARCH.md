# Research and technology choices

Research window: **November 2026**. The goal was to build an independent
firmware around the best currently maintained upstream stack for the Allwinner
V3s and a 240 × 240 ST7789-class panel, not to extend a vendor BSP.

## Board findings

The mainline device tree for the RG Nano has been present since Linux 6.7. It
describes:

- an Allwinner **V3s** with 64 MB RAM;
- a **240 × 240** panel on SPI0 using `panel-mipi-dbi-spi` with the panel
  compatible `saef,sftc154b`;
- an 80-pixel horizontal back porch to compensate for the controller's
  non-visible RAM;
- DC on **PC0**, reset on **PB2**, backlight through the V3s PWM;
- a **pcal6416** I2C GPIO expander for the face buttons and shoulders;
- an **AXP209** PMIC with battery and charger nodes;
- a **PCF8563** RTC;
- the V3s audio codec with a speaker amplifier enable on **PF6**;
- USB OTG and a UART console.

Because the board is already described upstream, TinyOS does not need a private
board file or a vendor kernel. The build uses the in-tree DTS and only adds
kernel configuration and the panel init firmware.

## Why `panel-mipi-dbi` instead of a dedicated ST7789 driver

The panel controller is an ST7789V-class device, but the mainline DRM ST7789V
driver work is not the stable path for this panel in the 6.12 LTS window. The
generic `panel-mipi-dbi-spi` driver is already used by the RG Nano device tree,
accepts a compact binary init sequence, and integrates with DRM fbdev. TinyOS
therefore ships a small, reviewable init blob and uses the panel through the
same path as the upstream board description.

The init sequence in
`buildroot-external/board/rg-nano/firmware/saef,sftc154b.txt` is a conservative
ST7789V bring-up (sleep out, MADCTL, porch, gamma, inversion, display on). The
first hardware unit must confirm colour order, inversion and orientation. Those
are documented as tuning points, not hidden assumptions.

## Why Linux + Buildroot

The V3s has an MMU, 64 MB RAM and a mature mainline port. A Linux firmware gives
the project:

- a maintained DRM panel driver and fbdev compatibility;
- evdev input, sysfs power/thermal telemetry and ALSA;
- the ability to add modules as ordinary C code;
- reproducible builds and a familiar debugging path over UART.

Buildroot was chosen over a hand-rolled rootfs because it pins the toolchain,
kernel, U-Boot and userland in one configuration, produces a complete image and
keeps the board support in a separate `br2-external` tree. musl keeps the
userland small without giving up pthreads or ALSA.

## Why LVGL 9.6

LVGL 9.6 provides the modern object/style API, RGB565 partial rendering, the
Montserrat font set, flex layouts and a small memory footprint. The UI uses a
256 KB LVGL heap, two 40-line draw buffers (about 38 KB total) and no image
decoder, GPU or browser engine. The display is driven through fbdev with dirty
rectangles.

The configuration is generated by `tools/gen_lv_conf.py`, so the enabled fonts,
color depth and feature flags are explicit and reviewable rather than hidden in
a large vendored config.

## Display path

```text
LVGL RGB565 draw buffers
        │ flush callback
        ▼
/dev/fb0 (DRM fbdev emulation)
        │ mmap + dirty pages
        ▼
panel-mipi-dbi-spi → SPI0 → ST7789V panel
```

The mainline driver exposes a 16-bit fbdev. The TinyOS backend also handles a
32-bit fbdev by expanding RGB565 to XRGB8888, which keeps the simulator and
future kernel configurations working.

## Audio path

The V3s codec driver creates its own ACPI/OF sound card; no extra machine driver
is required. TinyOS opens ALSA `default`, converts mono WAV to stereo on the
fly, writes 1024-frame chunks from a dedicated thread and controls the codec
through the ALSA mixer. WAV files are scanned from `/usr/share/tinyos/music` and
`/data/music`.

## Input path

The pcal6416 expander is handled by the kernel `gpio-pca953x` and `gpio-keys`
drivers. TinyOS reads `/dev/input/event*` non-blocking, maps Linux key codes to
LVGL keypad keys and keeps one pending key per poll. This avoids a custom
kernel driver and keeps the mapping in user space.

## Power and performance

- Battery percentage and charging state come from the AXP209 power-supply
  class.
- Brightness is written to `/sys/class/backlight/*/brightness`.
- Performance profiles write the cpufreq governor:
  `powersave`, `schedutil` (fallback `ondemand`) or `performance`.
- Temperature and memory statistics come from thermal zone 0 and
  `/proc/meminfo`.

## Constraints

| Constraint | Consequence |
|---|---|
| 64 MB RAM | no browser, no GPU stack, no large image caches |
| 240 × 240 | deliberate large type, one primary action per screen |
| 10 buttons | focus-based navigation, no touch assumptions |
| SD boot | keep boot assets in a small FAT partition |
| No network | all content is local; USB is the transfer path |
| 1.0–1.2 GHz | partial redraws and short animations only |

## Validation levels

1. **Host:** simulator renders all screens as PNG.
2. **Compile:** shared and Linux sources compile for ARM musl.
3. **Image:** Buildroot CI produces the complete SD image.
4. **Hardware:** still required for panel, keys, audio, PMIC and thermal.

The last level is intentionally called out as unverified in the README and in
the hardware notes.
